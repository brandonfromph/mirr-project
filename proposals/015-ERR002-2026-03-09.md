## Motivation

The MIRR compiler currently stops at the **first error** encountered in any pass. A designer writing a 200-line `.mirr` file with 5 typos must fix one, recompile, fix the next, recompile, and repeat 5 times. Every modern compiler (rustc, gcc, clang, javac) reports multiple errors per compilation. This is the single biggest UX gap in the MIRR developer experience.

**Current behavior:**

```
$ mirr-compile bad.mirr
error[E204]: Guard 'check_temp' references undeclared signal 'tmep'.
 --> bad.mirr:8:5
  |
8 |         when tmep > 100
  |     ^^^^^^^^^^^^^^^^^^^
```

One error. The designer fixes `tmep` → `temp`, recompiles, and gets a *different* error about a duplicate reflex name on line 20 that was always there.

**Target behavior:**

```
$ mirr-compile bad.mirr
error[E204]: Guard 'check_temp' references undeclared signal 'tmep'.
 --> bad.mirr:8:5
  |
8 |         when tmep > 100
  |     ^^^^^^^^^^^^^^^^^^^

error[E203]: Duplicate reflex name: 'respond'.
  --> bad.mirr:20:5
   |
20 |     reflex respond {
   |     ^^^^^^^^^^^^^^^^

error[E602]: Assignment to 'output' (u8): expression type bool is not compatible.
  --> bad.mirr:25:9
   |
25 |         output = alarm_active;
   |         ^^^^^^^^^^^^^^^^^^^^^

error: aborting due to 3 previous errors
```

All recoverable errors in one pass. The designer fixes everything and the next compile succeeds.

**Infrastructure readiness:** The `Diagnostic` struct, span tracking, source-snippet rendering, and LSP `publishDiagnostics` (which already accepts `Vec<Value>`) all exist from ERR-001/VSCODE-001. The change is architectural: making validation/typeck passes accumulate errors instead of returning on first failure, and threading `Vec<MirrError>` through the pipeline.

**Not in scope:** Making the pipeline continue from one pass to the next after errors (e.g., continuing to type-check after semantic validation fails). Each pass still gates the next pass. The change is **intra-pass accumulation**: semantic validation collects all duplicate names, all undeclared references, etc. before returning.

## Risk & Constraint Analysis

### Risks

| # | Risk | Severity | Mitigation |
|---|------|----------|------------|
| R1 | Changing `run_pipeline` return type breaks all callers | High | Update all call sites in same wave: CLI, LSP, tests, fuzz targets |

## Section C: Accumulating Type Checker — `src/typeck/mod.rs`

Change `typecheck_module()` to accumulate inter-expression type errors.

| # | Change | Rationale |
|---|--------|-----------|
| C1 | Change signature: `pub fn typecheck_module(module: &Module) -> Result<TypeMap, PipelineErrors>` | Multi-error return |
| C2 | Guard condition type check (E601): push to errors + `continue` to next guard instead of `return Err` | Report all guard type errors |
| C3 | Assignment type check (E602): push to errors + `continue` instead of `return Err` | Report all assignment type errors |
| C4 | Property formula type checks: push to errors | Report all property type errors |
| C5 | Inner `infer_expr_type()` calls: remain fail-fast with `?` — convert single `MirrError` to push into accumulator via `match`/`if let Err(e)` | Intra-expression errors cascade (parent type depends on child type), so fail-fast within a single expression tree is correct |
| C6 | At end: if errors non-empty, return `Err(PipelineErrors::from(errors))`; else return `Ok(all_types)` | Return accumulated or success |

Key design: **inter-expression accumulation, intra-expression fail-fast**. If guard A has a type error, we still check guard B. But within a single expression tree, we stop at the first error.
