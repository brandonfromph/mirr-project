# MCP Server Roadmap for NASA-Rust EDA

This document outlines the long-term plan for the custom Multi-Channel
Protocol (MCP) server that powers the NASA‑Rust EDA workspace. The goal is to
provide a safe, extensible, and auditable interface for agents and tools to
interact with the repository and toolchain.

## Vision

> Build a hardened, extensible MCP server that safely exposes file operations,
> search, build/test tooling, and other EDA-specific helpers to local agents
> and IDEs. Provide strong sandboxing, role-based access, and observability
> while keeping the transport simple (stdio on Windows, TCP/pipe on other hosts)
> and the API modular. Ultimately serve as the "glue" between human/AI
> assistants and the MIRR compiler/toolchain.

## Phased Goals

1. **Phase 0 – Prototype** (completed)
   - Basic file read/write, health, null-result unknown-method fallback
   - stdio‑direct transport only

2. **Phase 1 – Core Safety & API**
   - RBAC & API key handling
   - Path whitelisting and safe resolution
   - Concurrency limits per token
   - JSON schema validation (AJV)

3. **Phase 2 – Tooling & EDA Features**
   - Safe `run_cargo`, `search_files`, `directory_tree`
   - MIRR-specific helpers (temporal guard compile, parity check, etc.)

4. **Phase 3 – Sandboxing & Resource Control**
   - CPU/memory/time limits on child processes
   - Docker/VM sandbox mode option
   - Kill-on-timeout behavior

5. **Phase 4 – Observability & Reliability**
   - Structured audit logs (JSONL+HMAC)
   - Metrics/health endpoints (Prometheus)
   - Graceful shutdown and service examples (Windows, systemd)

6. **Phase 5 – Client Ecosystem & Docs**
   - CLINE/VS Code configuration examples
   - MCP Inspector/debug tool
   - Developer docs and API spec

7. **Phase 6 – Research & Expansion**
   - Templates, sampling, experiment workflows
   - AI/ML-driven code generation support
   - Remote/cluster operation (future)

## Guiding Principles

- **Security first**: Operations must not allow workspace escape or host
  compromise.
- **Workspace-centric**: All paths and actions are scoped to the configured root.
- **Simple transport**: Support stdio, pipes, or TCP; avoid complex protocols.
- **Pluggable tools**: Easily add or remove methods without core changes.
- **Observability & auditability**: Log every request with context.
- **Compatibility**: Unknown methods should not break clients (see null-result
  fallback).

## Documentation & Tracking

- `PRODUCTION_CHECKLIST.md` will track implementation status of safety items.
- Each phase may spawn its own subdocument (e.g. `mcp_phase2_tasks.md`).
- This roadmap should be revisited periodically as requirements evolve.
